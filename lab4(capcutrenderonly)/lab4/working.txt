3. `client/protocol.py` & `server/protocol.py` (HEADER FORMAT & RECVALL)
--------------------------------------------------------------------------------
Client aur Server dono k folders mai symmetrical `protocol.py` mojood hai taake
dono modules self-contained hon aur circular dependencies k baghair direct run ho sakein.

Code Highlights:
```python
MAGIC_BYTES = b"DC"            # 2 Bytes Magic ("Distributed Compute")
HEADER_FORMAT = ">2s2sI"        # Big-Endian: 2s (Magic), 2s (MsgType), I (Length uint32)
HEADER_SIZE = struct.calcsize(HEADER_FORMAT)  # Exact 8 bytes
CHUNK_SIZE = 64 * 1024          # 64 KB chunk size for high-speed streaming
SOCKET_TIMEOUT = 15.0           # 15 seconds read timeout
PROTOCOL_VERSION = "2.0.0"      # Protocol handshake version
```

- TCP Stream Fragmentation ka Hal:
  TCP stream-oriented protocol hai jo message boundaries maintain nahi karta (yani multiple
  packets coalesce ho sakte hain ya single packet chotay fragments mai cut sakta hai).
  Is maslay ko solve karne k liye hamara custom framing protocol har packet se pehle exact
  8 bytes ka binary header attach karta hai:
  1. `MAGIC_BYTES (2 Bytes = b"DC")`: Protocol verification guard. Agar network par koi
     foreign scanner ya corrupt packet aaye to receiver pehle 2 bytes check karke foran drop
     kar deta hai.
  2. `MSG_TYPE (2 Bytes ASCII)`: Opcode jo packet ka action define karta hai (e.g. `b"HS"`, `b"FC"`).
  3. `PAYLOAD_LENGTH (4 Bytes uint32)`: Big-endian integer jo incoming data ka exact size
     (0 bytes se 4,294,967,295 bytes / 4 GB) batata hai.

- Zero-Copy Robust `recvall(sock, num_bytes)`:
  Standard `sock.recv()` aksar requested bytes se kam data return karta hai.
  Hamara `recvall()` memoryview slicing use karta hai:
```python
def recvall(sock: socket.socket, num_bytes: int) -> bytes:
    buffer = bytearray(num_bytes)
    view = memoryview(buffer)
    received = 0
    while received < num_bytes:
        chunk = sock.recv_into(view[received:], num_bytes - received)
        if chunk == 0:
            raise ConnectionResetError("Connection closed unexpectedly by remote peer.")
        received += chunk
    return bytes(buffer)
```
  Yeh function zero intermediate copies k sath guaranteed exact `num_bytes` buffer mai lata hai.

- `send_packet()` & `read_packet()`:
  - `send_packet(sock, msg_type, payload)`: Header pack karta hai (`struct.pack(">2s2sI", ...)`)
    aur socket par `sock.sendall(header + payload)` se atomic push karta hai.
  - `read_packet(sock)`: Pehle `recvall(sock, 8)` se header parhta hai, magic check karta hai,
    aur phir `recvall(sock, length)` se complete payload unpack karta hai.
  - `send_json()` & `read_json()`: Dictionaries ko UTF-8 JSON bytes mai serialize/deserialize kartay hain.

--------------------------------------------------------------------------------
| Opcode | Byte Constant | Name | Direction | Description |
| :--- | :--- | :--- | :--- | :--- |
| `HS` | `b"HS"` | `HANDSHAKE_SYN` | Client $\rightarrow$ Server | Handshake initiation with Client ID & Version |
| `HA` | `b"HA"` | `HANDSHAKE_ACK` | Server $\rightarrow$ Client | Handshake response with Server specs & hardware |
| `PI` | `b"PI"` | `PING_REQ` | Client $\rightarrow$ Server | Latency measurement probe with client timestamp |
| `PO` | `b"PO"` | `PONG_RESP` | Server $\rightarrow$ Client | Latency response with mirrored timestamp |
| `JS` | `b"JS"` | `JOB_SUBMIT` | Client $\rightarrow$ Server | Job metadata, multi-part parts list & render config |
| `JA` | `b"JA"` | `JOB_ACCEPTED` | Server $\rightarrow$ Client | Worker confirmation readiness for streaming upload |
| `FC` | `b"FC"` | `FILE_CHUNK` | Bi-directional | Raw binary segment (64 KB) of video asset or output |
| `FE` | `b"FE"` | `FILE_EOF` | Bi-directional | End-Of-File marker carrying expected SHA-256 hash |
| `PR` | `b"PR"` | `PROGRESS` | Server $\rightarrow$ Client | Live progress telemetry (FPS, %, Speed, ETA) |
| `JR` | `b"JR"` | `JOB_RESULT` | Server $\rightarrow$ Client | Completion metrics, output size, logs & SHA-256 |
| `DR` | `b"DR"` | `DOWNLOAD_REQ` | Client $\rightarrow$ Server | Request to stream rendered output or server log |
| `CR` | `b"CR"` | `CANCEL_REQ` | Client $\rightarrow$ Server | Gracefully abort active job and kill FFmpeg process |
| `FL` | `b"FL"` | `FILE_LIST_REQ` | Client $\rightarrow$ Server | Request list of shared files in server storage |
| `FR` | `b"FR"` | `FILE_LIST_RESP`| Server $\rightarrow$ Client | Return array of shared files with sizes and dates |
| `FU` | `b"FU"` | `FILE_SHARE_UP` | Client $\rightarrow$ Server | Initiate peer-to-peer file upload to shared hub |
| `FA` | `b"FA"` | `FILE_SHARE_ACK`| Server $\rightarrow$ Client | Acknowledge shared file upload completion |
| `ER` | `b"ER"` | `ERROR` | Bi-directional | Error payload with failure reason |

5. `client/utils.py` & `server/utils.py`
--------------------------------------------------------------------------------
Yeh modules shared cryptographic, formatting aur system discovery functions provide kartay hain:

- `natural_sort_key(s: str)`:
  Standard Python `sort()` filenames ko ASCII alphabetical order mai sort karta hai:
  `["part1.mp4", "part10.mp4", "part2.mp4"]` -> Jo video concatenation ka sequence kharab kar deta hai.
  `natural_sort_key` regular expression `re.split(r'(\d+)', s)` use karke human natural order enforce karta hai:
  `["part1.mp4", "part2.mp4", "part10.mp4"]` -> Perfect playback sequence!

- `compute_sha256(filepath, chunk_size=128*1024)`:
  File ko 128 KB chunks mai read karke SHA-256 hash banata hai.
  Multi-Gigabyte files par bhi RAM exhaustion nahi hoti.

- `get_ffmpeg_binary()`:
  System par best available FFmpeg binary locate karta hai:
  1. `FFMPEG_PATH` environment variable override check karta hai.
  2. `imageio_ffmpeg` library ka binary path check karta hai.
  3. System PATH environment variable fallback use karta hai.

- `detect_system_capabilities()`:
  Worker node ki dynamic hardware specs probe karta hai:
  - Hostname, OS platform (`Windows 10 AMD64`), Logical CPU cores count (`os.cpu_count()`).
  - FFmpeg presence: `ffmpeg -version` chala kar verify karta hai.
  - NVIDIA NVENC hardware encoder probe: `ffmpeg -encoders` stdout parse karta hai.
    Agar `h264_nvenc` mil jaye to GPU hardware acceleration mark hoti hai:
    `"NVIDIA NVENC Hardware Supported (Fast GPU Transcoding)"`.
    Warna fallback: `"Multi-Threaded CPU Encoding (libx264)"`.
  - CUDA / PyTorch check: `torch.cuda.is_available()` probe karta hai.

- `get_all_local_ips()` (`server/utils.py` & `client/utils.py`):
  Computer k tamam active network adapters ko scan karta hai:
  1. UDP socket connect probe (`10.255.255.255:1`).
  2. `socket.gethostbyname_ex` multi-homed adapter enumeration.
  3. Windows-specific `ipconfig` parsing: Tamam static IPv4 addresses ko capture karta hai
     aur APIPA link-local addresses (`169.254.x.x`) ko filter out karta hai taake sirf
     usable genuine LAN IPs display hon.

- `generate_sample_video(...)`:
  OpenCV ya FFmpeg synthetic pattern (`testsrc` / `lavfi`) k zariye dynamic moving timer,
  color bars, aur audio tone wali standard MP4 video generate karta hai.


6. UNIVERSAL WINDOWS VIDEO COMPATIBILITY GUARANTEES
--------------------------------------------------------------------------------
Aksar FFmpeg renders standard Windows Media Player ya default "Movies & TV" app par
black screen ya error `"0xc00d36c4: This file isn't playable"` dete hain.
Hamari implementation mai 3 critical engineering guarantees shamil hain:

1. Pixel Format (`-pix_fmt yuv420p`):
   Default libx264/NVENC aksar high-bit-depth (YUV444p ya 10-bit) choose kar lete hain
   jo consumer video players par nahi chalti. Hamara engine output ko strictly **`yuv420p`**
   (Baseline/High Profile) par convert karta hai.
2. Even Pixel Dimension Enforcement:
   libx264 odd dimension (e.g. 721x481) par crash kar jata hai. Hamara filter chain:
   `scale=trunc(iw/2)*2:trunc(ih/2)*2` ensure karta hai k width aur height hamesha even hon.
3. FastStart Container Atom (`-movflags +faststart`):
   Default MP4 files mai metadata index (`moov` atom) file k aakhir mai hota hai jis se player
   ko puri file load hone tak wait karna parta hai. `-movflags +faststart` index atom ko
   file k bilkul start par shift kar deta hai, jis se Windows Media Player par INSTANT playback shuru hoti hai!

9. `server/network_server.py` (MULTI-THREADED TCP LISTENER & DISPATCHER)
--------------------------------------------------------------------------------
- Main Listener Loop (`start()`):
  `self._server_sock.bind((self.host, self.port))` aur `self._server_sock.listen(10)`.
  Incoming client aane par:
  ```python
  handler_thread = threading.Thread(
      target=self._handle_client_connection,
      args=(client_sock, client_addr),
      daemon=True
  )
  handler_thread.start()
  ```
  Main listener thread kabhi block nahi hota; har client independent thread mai run hota hai.

- Automatic Startup Diagnostics:
  Server start hone par:
  1. `get_all_local_ips()` call karke Computer A k liye exact LAN IPs terminal par print karta hai.
  2. APIPA check run karta hai; agar `169.254.x.x` detect ho to prominent warning deta hai
     aur `setup_lan_ip_server.bat` run karne ki hidayat deta hai.
  3. Port 5000 firewall allowance remind karta hai.

- Interactive Session Handling (`_handle_client_connection`):
  * `client_sock.settimeout(None)`: Interactive GUI sessions k liye idle timeout disable rakhta
    hai taake client parameters customize karte waqt disconnect na ho.
  * Message Loop:
    1. `MsgType.HANDSHAKE_SYN`:
       Client identity register karta hai aur Server specs ka JSON ACK return karta hai.
    2. `MsgType.PING_REQ`:
       Client timestamp k sath foran `MsgType.PONG_RESP` bhejta hai (RTT Latency probe).
    3. `MsgType.JOB_SUBMIT`:
       Multi-part video metadata read karta hai, `JOB_ACCEPTED` bhejta hai, streamed chunks
       disk par write karta hai, SHA-256 hashes verify karta hai, aur execution engine ko invoke karta hai.
    4. `MsgType.DOWNLOAD_REQ`:
       Requested output video ya server render log file client ko 64 KB chunks mai stream karta hai.
    5. `MsgType.FILE_LIST_REQ` / `FILE_SHARE_UP`:
       LAN peer-to-peer file sharing hub requests process karta hai.
    6. `MsgType.CANCEL_REQ`:
       Running transcode aur child FFmpeg process ko kill karta hai.

18. CAPCUT EXPORT WATCHER → COMPUTER B REMOTE RE-ENCODE (TAB 3)
--------------------------------------------------------------------------------
Tab 3 is a dedicated post-export bridge. It does NOT inject into CapCut's Export
button and it does NOT move CapCut's proprietary timeline renderer to Computer B.
CapCut first creates its normal MP4 export on Computer A. This application then
observes the configured export folder, waits until the file is non-empty and its
size/mtime signature remains unchanged for three 2-second polls, and adds the file
to a queue. The client uploads it to Computer B over the same framed TCP protocol.
Computer B runs FFmpeg with NVENC only when the system FFmpeg/NVIDIA probe passes;
otherwise it uses the CPU libx264 encoder. The rendered MP4 and log are downloaded
to Computer A and the output size + SHA-256 are verified.

- Same-name exports are detected because the watcher compares size + high-resolution
  modification time, rather than tracking filenames only.
- Multiple completed exports are queued and processed one at a time; they are not
  dropped while another remote render is active.
- The source export is not deleted or changed. CapCut effects, transitions, titles,
  overlays and audio remain baked into the exported source MP4.
- Draft Explorer reads basic draft metadata and referenced video source paths only.
  It does not reconstruct all CapCut timeline tracks, effect parameters, keyframes,
  transitions, audio, text or stickers. The Draft Clips action therefore sends only
  referenced video sources, not a complete CapCut project render.
- For real GPU encoding, Computer B requires a supported NVIDIA GPU, NVIDIA driver,
  and NVENC-enabled FFmpeg on PATH (or FFMPEG_PATH). Bundled imageio-ffmpeg is only
  a fallback and may be CPU-only.
- Completed output is returned into Computer A's persistent client_downloads folder.

25. DIRECT LAN WIRE SETUP & WHY "UNABLE TO CONNECT" OCCURS
--------------------------------------------------------------------------------
Aksar jab do computers ko direct RJ-45 LAN cable se connect kiya jaye to IP theek lagne
k bawajood "Unable to connect" error aata hai. Is ki 3 bunyadi technical reasons hain:

1. APIPA (Automatic Private IP Addressing - 169.254.x.x):
   - Jab koi DHCP router mojood na ho to Windows dono machines ko `169.254.x.x` subnet
     par random link-local addresses assign kar deta hai.
   - Result: Dono computers deterministic static IP par nahi hotay aur ek doosray k
     existence ko verify nahi kar patay.

2. Unidentified Network Profile:
   - Direct LAN wire connection ko Windows "Unidentified Network" mark karta hai aur by
     default **Public Network Profile** assign kar deta hai.

3. Windows Firewall Inbound Blocking:
   - Public network profile par Windows Defender Firewall tamam incoming connections
     (including TCP Port 5000 and ICMP Ping requests) ko silently drop kar deta hai.
   - Result: Client timeout (`WinError 10060`) ho jata hai.

KAISAY RESOLVE KIYA GAYA (THE COMPLETE FIX):
- Step A: Computer A (Client) par `setup_lan_ip_client.bat` chalayein -> Static IP `192.168.1.10` set ho jata hai.
- Step B: Computer B (Server) par `setup_lan_ip_server.bat` chalayein -> Static IP `192.168.1.20` set ho jata hai.
- Step C: Dono scripts automatically Port 5000 aur Ping ka Firewall hole open karti hain.
- Step D: Computer A se `ping 192.168.1.20` karein -> 0.28 ms round-trip time response aayega!
